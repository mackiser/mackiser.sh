## Background

Linux won't pass traffic from one network interface to another unless IPv4 forwarding is turned on. That's controlled by a kernel setting, `net.ipv4.ip_forward`, and any host that routes traffic needs it set to `1`.

The usual way to make that stick was to `echo` the setting into a file under `/etc/sysctl.d/` with `tee`. On Ubuntu 26.04, that approach stopped working for some sysctl values, while Ubuntu 24.04 hosts were still fine. I needed a replacement that only touched 26.04 hosts and left everything else exactly as it was.

## The approach

The job came down to two questions.

**How do I tell which hosts are on 26.04?** Ansible gathers facts about every host before it runs anything, including the OS family, distribution and major version. Gating the task on those facts means every other host gets skipped.

**How should the file get written?** I could have used `command`, `template` or `copy`. I went with `copy` and inline `content`. It only rewrites the file when the content changes, so it's idempotent, and it doesn't need a separate template file.

Here's the core task:

```yaml
- name: Ensure /etc/sysctl.d/99-forwarding.conf enables ip_forward (Ubuntu 26 only)
  ansible.builtin.copy:
    dest: /etc/sysctl.d/99-forwarding.conf
    content: |
      net.ipv4.ip_forward = 1
    owner: root
    group: root
    mode: "0644"
  when:
    - ansible_facts['os_family'] == 'Debian'
    - ansible_facts['distribution'] == 'Ubuntu'
    - ansible_facts['distribution_major_version'] == '26'
```

The file is named `99-forwarding.conf` so it loads last and overrides anything earlier in `/etc/sysctl.d/`. I also read the facts through `ansible_facts['distribution']` rather than the older top-level `ansible_distribution` variables, which Ansible is phasing out.

Once it worked as a playbook, I turned it into a reusable role. The setting name, value and file path all live in `defaults/main.yml`, so they can be overridden in the inventory, in `group_vars` or with `-e`.

## Testing without a pile of VMs

I didn't want to stand up VMs every time I changed something, so the repo uses [Molecule](https://ansible.readthedocs.io/projects/molecule/). Running `just test` starts two throwaway containers, one on Ubuntu 26.04 and one on 24.04. It applies the role to both, checks the results and then removes them.

| Step          | Ubuntu 26.04                                             | Ubuntu 24.04   |
|---------------|----------------------------------------------------------|----------------|
| `converge`    | task `changed` (file written)                            | task `skipped` |
| `idempotence` | re-run reports `changed: 0`                              | --             |
| `verify`      | file exists, owned by root, mode `0644`, content correct | file absent    |

That proves the file is written correctly and only where it should be. It doesn't prove the kernel is actually forwarding packets, because Docker containers can't change network sysctls on the running kernel. For that part I used a real Ubuntu 26.04 VM:

```bash
# start from a known state
sudo sysctl -w net.ipv4.ip_forward=0

# run the playbook (the file is written, but the running value is still 0)
# then load the file
sudo sysctl -p /etc/sysctl.d/99-forwarding.conf
sysctl net.ipv4.ip_forward   # -> 1
```

## Applying it live

By default the role only writes the file, the same as the old `echo | tee` approach. The setting takes effect on the next reboot or `sysctl -p`. For hosts that need it right away, there's an opt-in flag, `sysctl_forward_apply_live: true`, that also sets the value on the running kernel with `ansible.posix.sysctl`.

Adding that flag turned up something useful. A colleague had reported that `ansible.posix.sysctl` was causing failures on Ubuntu 26 hosts in a separate role from Ansible Galaxy. Comparing that role's task with mine, the difference was `reload: true`:

```yaml
- name: Set ipv4_forward
  ansible.posix.sysctl:
    name: net.ipv4.ip_forward
    value: '1'
    sysctl_set: true
    state: present
    reload: true        # re-applies every sysctl on the host
  when: netplan_configuration.network.tunnels is defined
```

`reload: true` runs `sysctl --system`, which reapplies every sysctl setting on the machine. If any unrelated key is invalid or locked on the running kernel, the whole task fails, even when the forwarding setting itself applied fine.

So the live option here leaves `reload` out and sets only the one value. On a clean Ubuntu 26.04 VM it worked without any problems.
